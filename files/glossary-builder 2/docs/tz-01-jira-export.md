# ТЗ-01: экспорт тикетов из Jira и построение порядка обработки

## Роль агента

Ты пишешь **одноразовый CLI-скрипт** на Node.js (ESM, без TypeScript-сборки, `.mjs`). Скрипт выгружает тикеты из Jira, нормализует их и упорядочивает. Скрипт запускается многократно и должен быть идемпотентным.

Ты **не** анализируешь содержимое тикетов и не делаешь выводов о проекте. Твоя задача — только извлечение и нормализация данных.

## Что должно получиться

```
tools/glossary/
  jira-export.mjs        # скрипт
  config.json            # конфиг (создать шаблон)
  .cache/jira/           # сырые ответы, по файлу на тикет
  out/tickets.json       # итог
  out/tickets-report.md  # человекочитаемый отчёт о выгрузке
```

## Конфиг

```json
{
  "jira": {
    "baseUrl": "https://jira.example.com",
    "projectKey": "PROJ",
    "mode": "rest",
    "boardId": null
  },
  "scope": {
    "resolvedAfter": "2025-08-01",
    "includeUnresolved": true,
    "issueTypes": []
  },
  "output": {
    "redactEmails": true
  }
}
```

`issueTypes: []` означает «все типы». Не фильтруй по типу — тип пиши в поле, фильтровать будем позже.

## Режимы доступа

Поддержи два режима, оба пишут **один и тот же** `tickets.json`:

- `mode: "rest"` — Jira REST API, токен из переменной окружения `JIRA_TOKEN`. Предпочтительный режим.
- `mode: "manual"` — API недоступен. Скрипт не ходит в сеть, а читает готовые JSON-ответы, заранее сложенные в `.cache/jira/`. В этом режиме выгрузку делает браузерный агент или человек, а скрипт занимается только нормализацией и сортировкой.

Перед началом работы **проверь доступность REST API** и сообщи, какой режим применим. Не изобретай обходные пути авторизации.

## Извлекаемые поля

Для каждого тикета:

| Поле | Источник | Обязательное |
|---|---|---|
| `key` | `key` | да |
| `type` | `fields.issuetype.name` | да |
| `status` | `fields.status.name` | да |
| `resolution` | `fields.resolution.name` | нет |
| `summary` | `fields.summary` | да |
| `description` | `fields.description` | нет |
| `acceptanceCriteria` | кастомное поле, найти по имени | нет |
| `comments` | `fields.comment.comments[]` → `{author, created, body}` | нет |
| `labels`, `components` | одноимённые поля | нет |
| `epic` | epic link | нет |
| `sprints` | кастомное поле sprint → `[{id, name, number, state}]` | нет |
| `created`, `updated`, `resolutiondate` | одноимённые | да / да / нет |
| `linkedIssues` | `fields.issuelinks[]` → `[{key, type}]` | нет |

Имена кастомных полей (AC, sprint, epic) в разных инсталляциях Jira отличаются. **Не хардкодь `customfield_XXXXX`.** Определи их один раз через `/rest/api/2/field`, сопоставь по человекочитаемому имени и запиши найденные id в `config.json`, чтобы это было видно и правилось руками.

## Нормализация текста

Это половина ценности скрипта, отнесись серьёзно.

1. **Формат описания.** Jira Cloud отдаёт ADF (JSON-дерево), Jira Server — wiki-разметку. Определи формат и приведи оба к Markdown. Таблицы сохраняй как Markdown-таблицы, списки как списки, блоки кода как fenced-блоки.
2. **Вложения и картинки.** Тело картинки не тяни. Замени на маркер вида `[attachment: screen-2025-03-14.png]` — имя файла иногда несёт смысл.
3. **Упоминания** `[~username]` замени на `@username`.
4. **Пустые строки и служебный мусор** (панели, макросы, автоподписи ботов) вычищай, но веди список того, что вычистил, и покажи его в отчёте — я проверю, что не выкинуто лишнее.
5. **Комментарии ботов и CI** (интеграции, автостатусы) помечай `isBot: true`, но **не удаляй**.
6. Если `output.redactEmails: true` — заменяй email-адреса на `[email]`. Прочие персональные данные не трогай, но посчитай, в скольких тикетах встретились телефоны или похожее на ФИО клиентов, и напиши число в отчёт.

## Порядок обработки

Ключевое требование. Итоговый массив должен быть отсортирован так, чтобы более поздняя запись перекрывала более раннюю.

Правило сортировки:

1. **Первичный ключ — номер спринта, в котором тикет был завершён.** Тикет мог переезжать между спринтами, поэтому бери **последний** спринт из массива `sprints`. Номер извлекай из имени спринта регуляркой, вынесенной в конфиг (`sprintNumberPattern`, по умолчанию `/(\d+)/`).
2. **Вторичный ключ — `resolutiondate`.**
3. **Тикет без спринта:** размести по `resolutiondate` между спринтами — то есть присвой ему псевдономер спринта, равный номеру ближайшего спринта, чей интервал дат покрывает `resolutiondate`. Поставь `orderConfidence: "medium"`.
4. **Тикет без `resolutiondate`** (не завершён): используй `updated`, поставь в конец списка, `orderConfidence: "low"`.
5. Ничьих быть не должно: при полном совпадении сортируй по `key` (числовая часть, не строковая — `PROJ-9` идёт раньше `PROJ-10`).

Присвой каждому тикету итоговое поле `order` — целое число от 0. Именно оно будет определять последовательность запуска агентов.

## Требования к исполнению

- **Кэш обязателен.** Сырой ответ по каждому тикету сохраняй в `.cache/jira/<KEY>.json`. Повторный запуск не должен ходить в сеть за уже выгруженным. Флаг `--refresh` инвалидирует кэш.
- **Пагинация.** Не полагайся на дефолтный `maxResults`. Иди страницами до исчерпания, проверяй `total`.
- **Rate limiting.** Не более 5 запросов в секунду, экспоненциальный backoff на 429 и 5xx, максимум 5 попыток.
- **Только чтение.** Никаких POST/PUT/DELETE в Jira. Ни при каких условиях.
- **Прогресс** в stderr, результат в файлы. Скрипт должен переживать прерывание и продолжать с места остановки.
- Внешние зависимости — только если без них никак. Нативного `fetch` в Node 18+ достаточно.

## Отчёт `tickets-report.md`

Скрипт печатает:

- сколько тикетов выгружено, по типам и по статусам;
- разбивку по спринтам (номер → количество тикетов);
- сколько тикетов с `orderConfidence` не `high` и их список;
- сколько тикетов с пустым описанием;
- сколько тикетов, где описание короче 100 символов (кандидаты в «невнятные для агента»);
- список полей, которые не удалось сопоставить;
- список вычищенных при нормализации конструкций.

## Критерий приёмки

1. Скрипт отрабатывает на всём диапазоне без падений и без ручного вмешательства.
2. Я выбираю 5 тикетов наугад и сверяю их содержимое в `tickets.json` с Jira глазами — расхождений в тексте описания, AC и комментариев быть не должно.
3. Порядок первых 20 и последних 20 тикетов проверяю вручную на соответствие правилу сортировки.
4. Повторный запуск без `--refresh` не делает сетевых запросов и даёт побайтово тот же `tickets.json`.

## Чего делать не нужно

- Не анализируй смысл тикетов, не классифицируй, не суммаризируй.
- Не фильтруй тикеты по «полезности».
- Не ходи в git — это задача ТЗ-02.
- Не пиши тесты на весь скрипт; достаточно проверок на нормализацию ADF/wiki → Markdown.
