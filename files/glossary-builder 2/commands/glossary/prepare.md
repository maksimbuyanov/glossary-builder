Подготовь данные для сборки глоссария. Это детерминированный этап: работают
скрипты, ты только запускаешь их и читаешь отчёты.

**Шаг 1. Тикеты.**

```
node scripts/jira-export.mjs
```

Нет доступа к REST API — запусти `node scripts/jira-export.mjs --mode manual`.
В этом режиме скрипт в сеть не ходит, а читает готовые ответы из `.cache/jira/`;
положить их туда должен браузерный агент или человек.

Прочитай `out/tickets-report.md` и покажи человеку: сколько тикетов, сколько с
ненадёжным порядком, сколько с пустым или очень коротким описанием, какие поля
не удалось сопоставить.

**Шаг 2. Git.**

```
node scripts/extract.mjs
```

Скрипт может напечатать строку, начинающуюся с `!!! СТОП`. Это значит, что
слишком много коммитов без ключа тикета или слишком много тикетов без коммитов.

В этом случае **остановись и покажи вывод человеку**. Не подбирай настройки, не
включай merge-коммиты, не продолжай на своё усмотрение: схема привязки под
вопросом, и это меняет весь план работы.

**Шаг 3. Классификация.**

```
node scripts/classify.mjs
```

Прочитай `out/attribution-report.md` и разбери с человеком:

- распределение долей по децилям против текущего `targetShare` — если, например,
  медиана сильно ниже порога, порог завышен;
- топ-30 частотных файлов — это кандидаты в отдельные карточки инфраструктуры;
- тикеты, где все файлы ушли в noise, — обычно признак перекрученного фильтра;
- тикеты с большим числом файлов — рефакторинги, их разумно пропустить.

Пороги правятся в конфиге, после чего `classify.mjs` перезапускается за секунды.
`extract.mjs` при этом трогать не нужно.

Первый прогон почти наверняка даст перекос. Это нормально: калибровка порогов —
часть работы, а не признак поломки.
