# glossary-builder

Расширение для Qwen Code: собирает глоссарий проекта из тикетов Jira и коммитов
фронтового репозитория. Задумано как справочный слой поверх OpenSpec — чтобы агент
находил нужный модуль по описанию задачи и понимал, на что повлияет изменение.

Работает в закрытом контуре: **сеть не нужна ни на одном шаге**, кроме обращения
к вашей внутренней Jira. Внешних зависимостей нет — только стандартная библиотека
Node.js.

## Требования

- Node.js 18+ (проверено на 22)
- Git 2.30+
- Qwen Code с поддержкой расширений (`commands/`, `agents/`)
- Доступ к внутренней Jira (REST API или ручная выгрузка)

## Установка

```bash
qwen extensions install ./glossary-builder
# или, если переносите архивом:
qwen extensions install ./glossary-builder.tar.gz
```

Проверить: `/extensions` в интерактивном режиме, расширение `glossary-builder`
в списке. Команды появятся под `/glossary:*`, субагенты — в `/agents manage`
в разделе Extension Agents.

Скрипты запускаются из каталога расширения. Путь к нему виден в
`/extensions`; удобно один раз скопировать `scripts/` рядом с рабочим каталогом
или запускать по абсолютному пути.

## Порядок работы

```
/glossary:init      настройка конфига и глав (один раз, руками)
/glossary:prepare   выгрузка Jira + разбор git + классификация
/glossary:pilot     пилот на отобранных тикетах + сравнительный тест
/glossary:next      обработать следующий тикет
/glossary:terms     тикеты без фронтовых коммитов
/glossary:check     валидация
/glossary:status    где мы сейчас
```

Скрипты можно вызывать и напрямую:

```bash
node scripts/jira-export.mjs [--mode rest|manual] [--refresh]
node scripts/extract.mjs
node scripts/classify.mjs
node scripts/validate.mjs
node scripts/status.mjs [--done KEY] [--skip KEY] [--reset]
```

## Как это устроено

Разделение на два слоя — главное решение всей конструкции.

**Арифметика — скриптам.** Разбор git-истории, подсчёт долей в диффе, детект
форматирования, разрешение переименований, частотный фильтр. Всё детерминировано:
одинаковый вход даёт побайтово одинаковый выход, и результат можно проверить
глазами один раз, а не на каждом тикете.

**Смысл — агентам.** Что модуль делает, как это называется на языке бизнеса, какие
решения принимались. Это LLM умеет, а арифметику над диффами — плохо.

`extract.mjs` дорогой и запускается редко. `classify.mjs` дешёвый и перезапускается
за секунды при подкрутке порогов. Поэтому калибровка не требует перечитывания git.

Роль агентов «вычитки» и «сверки» выполняет `validate.mjs`: он проверяет, что
каждый файл в карточке действительно был в диффе указанного тикета. LLM плохо ловит
собственные галлюцинации, а эта проверка ловит их механически.

## Что оно НЕ делает

Стоит знать до начала.

- **Не восстанавливает разделение и слияние файлов.** Если файл разбили на два,
  git этого не покажет, и резервный проход тоже не покажет. Такие случаи попадают
  в `out/ambiguous-moves.json` на ручной разбор.
- **Не понимает семантику кода.** Классификация файлов — это арифметика над
  диффом. Файл, где поменяли одну важную строку, будет отнесён к `supporting`.
- **Не покрывает код старше выбранного диапазона.** Модули, которых не касались
  тикеты за период, останутся без карточек. Это осознанное ограничение дельта-подхода:
  чтобы покрыть остальное, нужен отдельный проход по коду.
- **Не заменяет `/opsx:onboard` из OpenSpec.** Тот делает baseline-спеки из кода,
  этот — справочник терминов и модулей из истории. Вещи дополняющие, а не
  взаимозаменяемые.
- **Не гарантирует качество на грязных участках.** Пилот на обособленной
  функциональности — это лучший случай.

## Ограничения по безопасности

- Скрипты выполняют только читающие git-команды (`log`, `show`, `ls-tree`,
  `rev-parse`). Рабочее дерево не меняется никогда.
- В Jira выполняются только GET-запросы.
- Запись идёт только в `out/`, `.cache/` и каталог глоссария.
- `output.redactEmails` скрывает email-адреса при нормализации. Прочие
  персональные данные из тикетов не фильтруются — если в вашей Jira они есть,
  проверьте это с безопасностью до первого прогона.
