
# ТЗ-02: привязка файлов к тикетам и отсев шума

## Роль агента

Ты пишешь **два CLI-скрипта** на Node.js (ESM, `.mjs`), работающих с локальным git-репозиторием фронтенда. Скрипты детерминированные: на одном и том же репозитории и конфиге дают побайтово одинаковый результат.

Ты **не** используешь LLM-рассуждения внутри скриптов и **не** пытаешься понять, что делает код. Всё решается арифметикой над diff-статистикой.

## Почему два скрипта, а не один

Разделение обязательно:

- `extract.mjs` — **дорогой и детерминированный**. Читает git, считает статистику, разрешает переименования. Результат — `raw-attribution.json`. Запускается один раз (и потом при обновлении репозитория).
- `classify.mjs` — **дешёвый и настраиваемый**. Читает `raw-attribution.json` + пороги из конфига, раскладывает файлы по ролям. Запускается сколько угодно раз.

Смысл: пороги отсева придётся подкручивать, и перекручивать их нужно за секунды, а не за полчаса перечитывания git-истории.

## Что должно получиться

```
tools/glossary/
  extract.mjs
  classify.mjs
  config.json
  out/raw-attribution.json     # выход extract
  out/path-history.json        # выход extract
  out/ticket-files.json        # выход classify
  out/files-index.json         # выход classify
  out/orphan-commits.json      # выход extract
  out/tickets-without-commits.json  # выход classify
  out/attribution-report.md    # выход classify
```

## Конфиг

```json
{
  "repo": { "path": ".", "ref": "HEAD", "includeMerges": false },
  "tickets": { "file": "out/tickets.json", "keyPattern": "PROJ-\\d+" },
  "exclude": {
    "paths": [
      "**/package-lock.json", "**/yarn.lock", "**/pnpm-lock.yaml",
      "**/*.snap", "**/__snapshots__/**",
      "**/*.md", "**/*.svg", "**/*.png", "**/*.jpg", "**/*.woff*",
      "**/dist/**", "**/build/**", "**/coverage/**", "**/*.generated.*"
    ]
  },
  "thresholds": {
    "targetShare": 0.4,
    "targetMinLines": 30,
    "targetMinLinesShare": 0.2,
    "importOnlyMaxShare": 0.1,
    "sharedTicketCount": 10,
    "hotTicketCount": 25,
    "featureMaxTicketCount": 5
  }
}
```

Все пороги — **только** из конфига. Ни одного магического числа в коде.

# Скрипт 1: `extract.mjs`

## Шаг 1. Индекс коммитов

Пройди историю от `repo.ref` вглубь, ограничившись диапазоном тикетов из `tickets.json` (самая ранняя дата `created` минус 30 дней — как нижняя граница).

Обязательно **одним батч-вызовом**, а не вызовом git на каждый коммит:

```
git --no-pager log <range> --no-merges --numstat --find-renames --find-copies \
  --date=iso-strict -z --format='%x01%H%x02%P%x02%aI%x02%an%x02%s%x02%b'
```

Парсить `-z`-вывод аккуратно: имена файлов могут содержать пробелы и не-ASCII. При переименовании `--numstat` отдаёт путь особым форматом (`old\0new\0`) — обработай его явно.

Ключи тикетов ищи в `subject` **и** в `body` (частая практика — `Refs:` в теле). Один коммит может относиться к нескольким тикетам — записывай все.

`includeMerges: false` по умолчанию. Но если обнаружишь, что значительная часть тикетов (>10%) не имеет обычных коммитов, а ключи есть только в merge-коммитах, — **остановись и сообщи мне**, не переключай режим сам.

## Шаг 2. Статистика по каждому изменению файла

Для каждой пары (коммит, файл) собери:

| Поле | Как получить |
|---|---|
| `added`, `deleted` | `--numstat` |
| `addedIgnoringWhitespace`, `deletedIgnoringWhitespace` | `git diff -w --ignore-blank-lines --numstat <sha>^ <sha> -- <path>` |
| `status` | `A` / `M` / `D` / `R` / `C` из `--name-status` |
| `renamedFrom` | при `R`/`C` |
| `isBinary` | `--numstat` отдаёт `-` вместо чисел |
| `importOnly` | все изменённые строки матчатся на `/^[+-]\s*(import|export)\b.*\bfrom\b/` |
| `commentOnly` | все изменённые строки матчатся на `/^[+-]\s*(\/\/|\/\*|\*)/` |

Для `importOnly` и `commentOnly` нужен построчный diff — тяни его **только** для файлов, у которых `added + deleted <= 50`, иначе это не окупается и такие файлы всё равно не попадут в шум.

Форматирование определяем так: если `addedIgnoringWhitespace + deletedIgnoringWhitespace === 0`, а `added + deleted > 0` — это чистое форматирование. Кавычки, точки с запятой и висячие запятые этим не ловятся; **не пытайся** писать нормализатор токенов, это отдельный проект. Вместо этого пометь флагом `punctuationOnlyCandidate: true` случаи, где количество добавленных строк равно количеству удалённых и все они попарно совпадают после удаления символов `'"`;,` — этого достаточно.

## Шаг 3. Разрешение переименований (важно)

Файлы переезжали при приведении к FSD. Тикет годичной давности ссылается на путь, которого в HEAD нет, — но файл жив по другому адресу. Это **не** повод считать запись невалидной.

Построй `path-history.json`:

1. Собери все события `R`/`C` из всей истории в хронологическом порядке: `{ sha, date, from, to }`.
2. Для каждого исторического пути прогони цепочку переименований вперёд до HEAD.
3. Проверь наличие итогового пути в дереве HEAD (`git ls-tree -r --name-only HEAD`).

Формат:

```json
{
  "src/components/UserCard.tsx": {
    "currentPath": "src/entities/user/ui/UserCard.tsx",
    "chain": [
      { "from": "src/components/UserCard.tsx", "to": "src/entities/user/ui/UserCard.tsx", "sha": "...", "date": "..." }
    ],
    "existsInHead": true
  }
}
```

Если путь до HEAD не доживает — `currentPath: null`, `existsInHead: false`, но запись всё равно сохраняется. **Удалённые файлы из выгрузки не выбрасывай** — проверка на удаление делается в самом конце, после сборки глоссария, и не здесь.

Понижение порога: вызывай `--find-renames=30%` вместо дефолтных 50%, значение вынеси в конфиг (`repo.renameThreshold`).

## Шаг 3b. Резервное распознавание переносов (обязательно)

Git восстанавливает переименования только **внутри одного diff**. В проекте есть переносы, которые он не увидит:

- файл перенесли и в том же коммите сильно переработали (схожесть ниже порога);
- удаление старого пути и создание нового попали в **разные коммиты** — здесь `--find-renames` не поможет никогда;
- файл разделили на два или слили два в один.

Поэтому после основного прохода сделай второй, по остаткам.

1. Собери все события `D`, которым не нашлось пары `R` внутри своего коммита → множество `orphanDeletes`.
2. Собери все события `A`, которым не нашлось пары → множество `orphanAdds`.
3. Сопоставляй их в таком порядке, первое сработавшее правило выигрывает:

   **Правило 1 — точное совпадение содержимого.** Возьми blob-хеш удалённого файла (`git rev-parse <sha>^:<path>`) и добавленного (`git rev-parse <sha>:<path>`). Если хеши равны — это гарантированный перенос без изменений. `confidence: "exact"`. Это самый частый случай при приведении к FSD и он ловится точно.

   **Правило 2 — совпадение имени файла.** Одинаковый basename, разные директории, окно ±90 дней между удалением и созданием, и в проекте нет других файлов с таким же basename в этом окне. `confidence: "high"`.

   **Правило 3 — схожесть содержимого.** Посчитай коэффициент Жаккара по множеству непустых строк (после `trim`) удалённого и добавленного blob. Порог из конфига (`repo.fallbackSimilarity`, по умолчанию 0.5), окно ±90 дней. `confidence: "medium"`.

4. Всё, что не сопоставилось, а также случаи, где на один `orphanDelete` претендуют несколько `orphanAdds`, — в `out/ambiguous-moves.json` с обеими сторонами и посчитанной схожестью. Это список для моего ручного разбора, **не угадывай**.

В `path-history.json` у каждого звена цепочки указывай `source: "git-rename" | "exact-blob" | "basename" | "similarity"` и `confidence`. По этим полям я смогу отличить надёжные звенья от предположительных.

Ограничение, которое надо честно указать в отчёте: разделение файла на два и слияние двух в один этой схемой не восстанавливаются. Такие случаи попадут в `ambiguous-moves.json` как «один delete, несколько add» — так и оставь.

# Скрипт 2: `classify.mjs`

## Шаг 1. Агрегаты

По тикету: `totalAdded`, `totalDeleted`, `fileCount` (без учёта `excluded`).
По файлу (глобально, по всей выгрузке): `ticketCount`, `commitCount`, `totalChurn`, `firstSeen`, `lastSeen`.

`share` файла в тикете = `(added + deleted) / (totalAdded + totalDeleted)` тикета.

## Шаг 2. Роль файла в тикете

Три значения: `target` | `supporting` | `noise`. Порядок правил — сверху вниз, первое сработавшее выигрывает. К каждому решению пиши `reason` строкой.

**noise**, если:
- `excluded` по маскам из конфига, или `isBinary`;
- чистое форматирование (`addedIgnoringWhitespace + deletedIgnoringWhitespace === 0`);
- `punctuationOnlyCandidate`;
- `commentOnly`;
- `importOnly` **и** `share < importOnlyMaxShare`.

**target**, если:
- `status` = `A` (файл создан в рамках тикета) или `R` (переименован);
- в тикете ровно один не-noise файл;
- `share >= targetShare`;
- `added + deleted >= targetMinLines` **и** `share >= targetMinLinesShare`.

Иначе — **supporting**.

## Шаг 3. Категория файла (частотный фильтр)

По `ticketCount` за весь период:

- `ticketCount <= featureMaxTicketCount` → `feature`
- `ticketCount >= hotTicketCount` → `hot`
- `ticketCount >= sharedTicketCount` → `shared`
- иначе → `mixed`

**Ключевое требование, не потеряй его.** Категория файла и роль в тикете — независимые оси. Файл может быть `shared` глобально и при этом `target` в трёх конкретных тикетах — именно эти тикеты объясняют, зачем этот файл существует, и именно они нужны в глоссарии.

Поэтому для каждого файла отдельно храни:

```json
"src/shared/api/client.ts": {
  "category": "hot",
  "ticketCount": 34,
  "targetTickets": ["PROJ-1010", "PROJ-1156"],
  "supportingTickets": ["PROJ-1204", "..."],
  "totalChurn": 1890,
  "firstSeen": "2025-02-11",
  "lastSeen": "2026-08-04",
  "existsInHead": true,
  "currentPath": "src/shared/api/client.ts"
}
```

`targetTickets` у `shared`/`hot` файла — это самый ценный сигнал во всей выгрузке. Никогда не отсеивай его вместе с шумом.

## Шаг 4. Выходные файлы

`ticket-files.json` — по тикету, отсортировано по `order` из `tickets.json`:

```json
{
  "PROJ-1204": {
    "order": 12,
    "commits": ["sha1", "sha2"],
    "target": [{ "path": "...", "currentPath": "...", "share": 0.62, "lines": 99, "reason": "share>=0.4" }],
    "supporting": [{ "...": "..." }],
    "noise": [{ "path": "...", "reason": "formatting-only" }]
  }
}
```

`tickets-without-commits.json` — список тикетов из `tickets.json`, для которых не нашлось ни одного коммита. Отдельный вход для другого агента, поэтому сохрани здесь же `key`, `type`, `summary` и `components`.

## Шаг 5. `attribution-report.md`

- сколько тикетов, сколько с коммитами, сколько без;
- распределение файлов по ролям (сколько всего target / supporting / noise);
- топ-30 файлов по `ticketCount` с их категорией и `targetTickets`;
- распределение `share` по децилям — по нему я буду калибровать пороги;
- список тикетов, где **все** файлы попали в noise (подозрительно — вероятно, ошибка классификации);
- список тикетов с более чем 40 не-noise файлами (вероятно, рефакторинг или мердж-бомба, требует ручного взгляда);
- количество «оборвавшихся» цепочек переименований.

## Ограничения на исполнение (жёсткие)

- **Только read-only git-команды**: `log`, `show`, `diff`, `ls-tree`, `rev-parse`, `cat-file`. Запрещено: `checkout`, `switch`, `reset`, `clean`, `fetch`, `pull`, `stash`, `gc`, любые `write`-операции и любые изменения файлов внутри репозитория.
- Все выходные файлы пишутся **только** в `tools/glossary/out/`.
- Скрипты не ходят в сеть.
- Внешние зависимости: допустима одна библиотека для glob-масок, остальное — стандартная библиотека Node.
- На репозитории в ~5000 коммитов `extract.mjs` должен отрабатывать за разумное время. Если упираешься — профилируй и уменьшай число вызовов git, а не сокращай объём собираемых данных.

## Критерий приёмки

1. Я даю тебе 5 тикетов, по которым знаю правильный ответ. Скрипт должен отнести к `target` ровно те файлы, которые я назову, — расхождения разбираем и правим пороги, а не код.
2. Повторный запуск `classify.mjs` с изменённым порогом занимает меньше 5 секунд.
3. Ни один файл в `ticket-files.json` не потерян: `target + supporting + noise` по каждому тикету равно полному списку изменённых файлов.
4. Ни одна запись не выброшена из-за отсутствия файла в HEAD.

## Чего делать не нужно

- Не пытайся понять смысл изменений. Никаких «этот файл про авторизацию».
- Не ходи в Jira — данные берёшь только из `tickets.json`.
- Не объединяй скрипты в один.
- Не заводи базу данных. JSON-файлов достаточно.
